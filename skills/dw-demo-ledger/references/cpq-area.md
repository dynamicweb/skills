# CPQ area contract

The CPQ area is a proposed acceptance inventory for app-backed CPQ on Truvio Commerce
(powered by Dynamicweb). It is not a claim that a platform release added these functions.
Every function is a candidate and every binding is planned. Inventory and schema validation
cannot establish runtime support, readiness or a passing configuration.

The source profile and seven authoring constraints are in
[engine-characterization.md](../../dw-commerce-cpq/references/engine-characterization.md).
The snapshot is revision 4, following the merged brand-gap inventory revision. [dw 10.29.8]
The earlier release snapshot and existing consumer locks remain unchanged.

Core predicates require the two exact vendor app versions recorded by that profile. Checks
that assert Studio also name its version. Loaded package/assembly identity, TFM and SHA-256
must be measured, not inferred from a filename. Resolve Studio's MCP and MCP host dependencies,
DOCX's OpenXml dependency and any exposed licence requirement before proof. The area neither
invents a compatible dependency release nor raises the base platform's MCP floor.

Structural intents prefer complete, equivalent external MCP observations, then authenticated
Admin queries discovered on the installed app. Neither a guessed tool/query nor a type in an
assembly is an executable binding. Studio's read/analyze pack requires the Dynamo request
context and administrator access; keep that restriction. SQL observations are local-only,
version-scoped reads for facts higher surfaces cannot expose. Denied, incomplete or unavailable
observations are UNVERIFIED, not an empty model or PASS.

Behavioral intents consume evidence from an isolated producer. The ledger checker never runs
save, copy, rename, cart, quote or document experiments itself. A future receipt reader must
bind complete observations to trusted host/release/run, loaded packages, concrete model/version,
model/spec/catalogue hashes and the exact ledger lock. It must compare independent golden
expectations, check freshness and retain raw failures. A valid receipt envelope is not a passing
behavioral result. Counts without subjects, stale evidence and a successful HTTP status without
an identified, correct destination record cannot pass.

The inventory covers installation, model versions, inputs, lookups, conditions, input rules,
constraints, BOM, pricing, persistence, revisions, cart, quotes, documents, page binding,
Studio authoring, diagrams and reproducible spec builds. Routing, CPQ visualization and ERP
have explicit optional grounds; a declared profile must prove them. Omitting ERP never waives
the local cart or quote checks. Shared catalogue, page, user, price, storage and Serializer
capabilities retain their existing platform function IDs.

The corresponding Distribution CPQ spec/package/behavior contracts are proposed authoring
contracts, not an installed feature layer or released edition. Keep the actual compiler,
producer, observation handlers and proof separate from these intent declarations. Enable a
binding only when its complete read and negative controls are implemented and tested.
